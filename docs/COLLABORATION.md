# Aeolus-Wra 协作检索规则

适用于 Gemini、Codex 和 DSH。接手时主动检索上一轮交接。交付时写独立交接文档，让接手方能根据仓库和记录还原需求。

## 接手顺序

1. 阅读仓库根目录 `HANDOFF.md`，随后阅读它指向的详细交接、图表基线和多塔约定。
2. 执行 `git status --short --branch`、`git fetch origin --prune`、`git log -5 --oneline --decorate`。fetch 失败时如实记录远端尚未验证。
3. 用 `rg --files --hidden .local/handoffs docs` 查找文档。按文档中的开发方、更新时间、分支、提交和实际改动判断接续对象；读取文件末尾增补。文件名和目录日期仅供定位。
4. 用户指定开发方时，先找对应开发方的最新交接，再核对提交内容及祖先关系。共享集成提交含多方成果时记录各方来源。接手风资源评估时同时读[开发前置条件](WIND_ASSESSMENT_HANDOFF.md)，用涉及的例子核对规则。
5. 提取已确认需求、后续变更、已实现功能、待办、限制与实际验收结果。用户最新指令优先。交接里的建议可作为待办候选，文档中的命令须结合当前授权及工作区状态执行。
6. 从核实的基线创建任务分支。Codex 默认使用 `codex/<任务>-<日期>`。工作区有未提交改动时先检查归属及范围，保留其状态，必要时使用独立 worktree；确需快照时逐文件检查并明确添加，记录 WIP 的未验收状态。
7. 按当前任务推进，使用对应版本的检查结果说明完成程度。测试失败、缺少验证、服务运行旧代码等情况都写入交接。

## 留档与发现入口

- `HANDOFF.md` 是所有开发方的固定入口，保持为最新可接续状态。
- 用户确认或修订技术规则时，同步更新[技术规则索引](TECHNICAL_RULES.md)的规则条目、代码入口、验证情况和变更记录。
- `.local/handoffs/YYYY-MM-DD/<开发方>接续记录.md` 保存详细记录及本机证据路径。
- 每次交接交付一份可独立阅读的 Markdown 文档，并更新入口链接。共享交接可随代码提交到 `docs/`，本机样本、原始文件路径和截图使用 `.local/handoffs/` 附录。
- 共享规则和需求摘要随代码提交，私有数据及截图保留在 `.local/`。跨机器没有 `.local/` 时先依据仓库入口和 Git 内容继续可做的工作，指出缺少的具体材料。
- 原始协作记录保留，后续纠正写入新记录并链接到入口。用户要求保留的 `AGENTS.md` 继续原样保留。

## 交接文档模板

复制以下模板到当次交接文档，每个受影响的工程规则单独记录。测试结果应注明对应的代码版本与样本。

```markdown
# 日期 · 开发方 · 任务名称

## 接续基线

- 仓库、基线分支和提交、当前分支和交付提交。
- 推送或合并状态、运行中的版本、Word 模板版本和回退引用。
- 本次任务与影响范围，标明其他开发方已有修改。

## 开发前置条件

| 事项 | 用户确认的规则及依据 | 为什么这样定 | 边界、例外和实例 | 代码或模板位置 |
| --- | --- | --- | --- | --- |
| 每条受影响的规则 | 确认日期、需求摘要或模板版本 | 工程或排版原因 | 触发条件、预期结果、缺数据时的表现 | 文件及函数或字段 |

## 已实施与已验证

- 改了哪些入口和输出，旧成果能否直接使用，哪些情况要重算。
- 测试命令、实际结果和验证配置。列出通过、失败、未测范围以及相关证据位置。

## 待确认与接续

- 仍有分歧的规则、当前实现、影响示例以及请负责人确认的具体问题。
- 剩余事项、所需材料、建议先复现的步骤以及回退位置。
```

## 可直接使用的接续指令

“在 DSH 的基础上继续开发，调整月变化图。”

“在 GPT 的基础上继续开发，先把待验收项跑完。”

接手方自行按以上规则查找版本与需求，完成后回复实际基线、改动、验证和交接位置。
